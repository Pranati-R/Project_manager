1What the gateway is

A gateway is one front door for many web projects. Instead of giving every project its own port that people must remember, all projects share one port, and each one gets its own path after it.

Without the gatewayWith the gateway
http://server:5173 (shop)
http://server:3000 (blog)
http://server:8000 (notes)		 http://server:8280/shop/
http://server:8280/blog/
http://server:8280/notes/

The gateway is made of nginx (a well-known web server) plus a dashboard that writes nginx's settings for you. Nobody edits nginx files by hand.

In one sentence

You tell the dashboard "the project shop runs on port 5173 and should appear at /shop/"; the dashboard builds and safely installs the nginx settings that make it so.

Why 127.0.0.1?

127.0.0.1 means "this same computer". A project that listens only there can be reached only through the gateway, so nobody can skip the gateway's rules (for example, who is allowed in).

3What happens when someone opens a project

Someone opens http://server:8280/shop/products:

  1. The browser asks the serverRequest goes to port 8280.
  2. nginx checks who is askingOnly devices on the allowed network (Tailscale and the server itself) get through. Others get "403 Forbidden".
  3. nginx reads the pathIt starts with /shop, so this belongs to the project shop.
  4. nginx forwards the requestTo the project at 127.0.0.1:5173, adjusting the path (see below).
  5. The project answersnginx sends the answer back to the browser.

Two ways of passing the path on

Path mode/shop/page reaches the project asUsed for
strip/page (project path removed)Built files served by nginx / Docker, or served by your own backend
subpath/shop/page (kept)Vite dev server, Vite preview, Next.js

Backend APIs work the same way. A request for /shop/api/users reaches the backend as /api/users, which is why a backend needs no change.

4How a project is added

In the dashboard, Projects → Add project. You fill in a name, the app type, the URL path and the port. Behind the scenes:

  1. You fill in the formFor example: name Shop, path /shop, App type Vite dev server, port 5173. The App type fills in the technical options for you.
  2. The manager checks every valueIs the path valid and unused? Is the port free and not used by another site? A mistake is shown next to the field and nothing changes.
  3. The project is savedIt is stored in the manager's own state file.
  4. The nginx settings are generatedThe manager builds one complete gateway config from all projects using a template.
  5. The change is tested and installedSee the next section: the config is tested, installed and nginx is reloaded.
  6. You press TestThe dashboard checks that the app answers, that the page loads through the gateway and that its files load from the right path.
Live preview

While you type, the form shows the nginx routes that will be created, so you can see the result before saving.

5How nginx is updated (safely)

The gateway's nginx settings live in one generated file: /etc/nginx/nginx-gateway/gateway.conf. It is written only by the helper, and only after the checks below. The rest of nginx (your other sites) is never edited.

1. Generatemanager builds the config from all projects
↓
2. Test in a private sandboxnginx -t on the new file alone
↓
3. Helper: lintonly the expected kinds of lines are allowed
↓
4. Helper: conflict scanno other site or program already uses these ports
↓
5. Back up the live filelast 30 versions are kept
↓
6. Replace the file in one stepthen nginx -t on the whole nginx setup
↓
7. Graceful reloadvisitors are not cut off; then it confirms nginx listens on the new ports
If any step fails

The previous file is put back, nginx keeps running with the old settings, and the dashboard shows what went wrong. A bad change never goes live.

Other things you can doHow
Undo a mistakeNginx config → Backups → Restore (tested first)
See what changedNginx config → Changes (a diff against the live file)
Update the gateway softwaresudo nginx-gateway-ctl update-code pulls the new code, restarts the manager and re-applies the config. It rolls back by itself if a step fails.

6How everything keeps running

  • nginx runs as the normal system service and serves the gateway on port 8280 and the dashboard on 8281.
  • The manager runs as a system service (nginx-gateway-manager) on 127.0.0.1:8790, as a limited account without a shell.
  • Your projects keep running the way you already start them (a terminal, systemd, or Docker). The gateway never starts or changes them. If you list an app in the restart list, the dashboard can restart it with one button.
  • The dashboard checks health every few seconds: a green dot means the project answers on its port.
  • Logs are in the dashboard's Logs tab: access log, error log, and an audit trail of who changed what.
  • Security basics: sign-in with passwords and sessions, protection against forged requests, only allowed networks can connect, and everything the helper may do is limited to a fixed list.

7What changes in your project (general example)

Under the gateway your project lives at /myapp/, not at /. Most frameworks write links that start with /, so the frontend must be told its base path. The backend is never told.

Without the base path

The page asks for /assets/app.js. That is outside /myapp/, so the gateway finds no project: blank page.

With the base path

The page asks for /myapp/assets/app.js. The gateway knows it belongs to myapp: the page loads.

What needs a change, and what does not

PartChange?What to do
Frontend (Vite, Next.js, React, Vue...)YesSet the base path (one flag or setting), then rebuild if it is a built app.
Backend (FastAPI, Flask, Express, Django...)NoNothing. Only make it listen on 127.0.0.1.
nginxNoThe dashboard does it.
DockerRebuildPass the base path as a build argument and rebuild the image.
An app you cannot changeNoGive it its own gateway port instead of a path.

Example: a Vite frontend with a backend

1. Start the frontend with its base path (this is the only frontend change for the dev server):

# before
npm run dev

# after
npm run dev -- --base /myapp/ --host 127.0.0.1 --port 5173 --strictPort

2. Start the backend as usual, only on 127.0.0.1:

uvicorn main:app --host 127.0.0.1 --port 8000      # code unchanged

3. Point the frontend at the API through the gateway (use the app's API variable if it has one, so no code changes):

VITE_API_BASE=/myapp/api npm run dev -- --base /myapp/ --host 127.0.0.1 --port 5173 --strictPort

4. Add the project in the dashboard:

SettingValue
URL path/myapp
App typeVite dev server
Frontend port5173
Separate API serverticked: port 8000, API path /api

5. Result:

Browser asks forGoes to
http://server:8280/myapp/the frontend
http://server:8280/myapp/api/usersthe backend, as /api/users (backend untouched)

Small code fixes, only if the app has them

// a router with real URLs (/settings, /profile)
<BrowserRouter basename={import.meta.env.BASE_URL}>

// code that writes /api/... or /logo.png
const API = import.meta.env.VITE_API_BASE || `${import.meta.env.BASE_URL}api`
<img src={`${import.meta.env.BASE_URL}logo.png`} />
One exception for backends

If the backend itself writes web pages or redirects (for example redirect("/login")), those links also need the path. Backends that only return JSON are not affected.

8Summary

  1. The gateway is one door (port 8280) with a path per project.
  2. You add a project in the dashboard; the manager builds the nginx settings from all projects.
  3. Every change is checked, backed up, tested and reloaded gracefully; a failure leaves the old settings running.
  4. Projects keep running as they are, on 127.0.0.1, so only the gateway can reach them.
  5. Your frontend needs its base path; your backend needs nothing.
The full step-by-step pages are in the dashboard under Docs (files in the docs/ folder).
